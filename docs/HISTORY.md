# История разработки и принятые решения

Конспект диалога с Claude Code (17.11.2026), в котором был написан проект.
Полная сырая история лежит в `.claude-history/` (в git не попадает, см. ниже).

## Исходная задача

Развитие проекта на STM32 — https://github.com/Ramzess-II/jikongUart.
Старая версия опрашивала BMS и выключала реле зарядки по проценту SOC, а в 23–7 включала зарядку по ночному тарифу.

Новое устройство:
- **ESP32-S3 Pico** на макетке, питание через DC-DC прямо от батареи (бесперебойное);
- **JK BMS JK-BD6A24S12P**, подключение по TTL UART;
- батарея **13S NMC**;
- реле зарядки управляется **по общему напряжению**, а не по SOC;
- сообщения в Telegram — по запросу и при пропадании сети.

## Требования (от пользователя)

1. **Пороги — на ячейку**, чтобы продлить жизнь АКБ:
   - 4.05 В/яч → выключить заряд (52.65 В для 13S);
   - 3.90 В/яч → включить (50.70 В).
2. **Ночной тариф сохраняется**, но с улучшением. В Украине свет отключают 3–4 раза в день, поэтому на ночную зарядку полагаться нельзя.
   - Нужен порог, по которому заряд включается и вне ночного тарифа, чтобы хватило продержаться определённое время.
   - Резерв — **минимум 4 часа**. Пользователь обещал рассказать подробности позже, это **ещё не сделано**.
3. **Определение пропадания сети** — по току BMS. Инвертор подключён к дому: при пропадании сети дом переходит на инвертор, и появляется ток разряда.
4. **Фильтр потребления.** Устройство считает, сколько дом потребляет в час (среднее), и прогнозирует, на сколько хватит заряда. На этом же строится принудительное включение заряда.
5. **Защиту по максимальной ячейке НЕ делать** — это делает сама BMS.
6. **Делать отказоустойчивость и watchdog.**
7. **Ботом пользуются два человека** — пользователь и его жена.
8. **Настройки задаются через веб-страницу** (Wi-Fi, токен и т.д.).
9. **Два дома.** Для этого нужны два бота в одной группе: один токен нельзя опрашивать с двух устройств, Telegram вернёт ошибку 409.

## Что реализовано

| Модуль | Что делает |
|---|---|
| `jk_bms.c` | Протокол JK «NW» (`4E 57 …`, CRC — 16-битная сумма), разбор полей 0x79–0xC0 |
| `control.c` | Цикл раз в 1 с: опрос BMS, детектор сети, решение по реле, уведомления, failsafe |
| `energy.c` | 24 почасовых EMA-корзины потребления. Обучаются только во время отключений и сохраняются в NVS |
| `telegram.c` | Long polling `getUpdates`, очередь отправки, несколько chat_id, фильтр `/cmd@botname` |
| `commands.c` | /status /cells /profile /charge_on /charge_off /auto /settings /profile_reset /help |
| `net.c` | Wi-Fi STA, точка доступа `JK-BMS-Setup` (нет связи 3 мин или BOOT 3 с), SNTP, часовой пояс Киева |
| `web.c` | Страница настроек с Basic-авторизацией; сохранение в NVS и перезагрузка |
| `settings.c` | Настройки в NVS с валидацией |

### Логика реле (порядок приоритетов)

1. Нет связи с BMS или нет сети → реле **OFF** (failsafe, срабатывает сразу).
2. Ручной режим `/charge_off` → OFF.
3. Напряжение ≥ порога OFF (4.05 В/яч) → OFF, ставится флаг «заряжена».
   - Флаг снимается, когда напряжение опускается ≤ порога ON (3.90 В/яч).
4. Ручной режим `/charge_on` → ON.
5. Авто, в порядке приоритета:
   1. **FORCE**: ≤ 3.60 В/яч → ON, выключается при > 3.70 В/яч.
   2. **RESERVE**: доступной энергии меньше, чем нужно на `reserve_h` часов по профилю. Гистерезис +15 %.
   3. **NIGHT**: ночной тариф и напряжение ≤ порога ON.
6. Реле переключается не чаще раза в 60 с (кроме аварийного OFF).

**Доступная энергия** = (SOC − min_soc) % × ёмкость × 13 × 3.7 В.
**Резерв** = энергия на ближайшие `reserve_h` часов по почасовому профилю.

### Watchdog и отказоустойчивость

- Task WDT 60 с с паникой → перезагрузка (было задумано 90, см. «Цикл перезагрузок» ниже).
- При старте реле в OFF ещё до `gpio_config`.
- BMS молчит 15 с → OFF и уведомление.
- Нет сети → заряд выключен.

## Обновление по воздуху (OTA), версия 1.1.0

Пользователь попросил оба способа: через веб-страницу и файлом в Telegram.

- **Разметка `partitions.csv` (4 МБ).** nvs на прежнем месте (0x9000, 24 КБ) — настройки переживают смену разметки. Дальше otadata и два слота `ota_0`/`ota_1` по 0x1E0000 (1.875 МБ). Прошивка 1.05 МБ, свободно 44 %.
- **Стандартная `TWO_OTA` не подходит**: там слоты по 1 МБ, а прошивка уже больше.
- **`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`.** `ota_tick()` в цикле управления подтверждает новую прошивку через ≥30 с, когда снова работает то, что работало до обновления: BMS, Wi-Fi, getMe. Флаги «что работало» сохраняются в NVS (`ota/pend`) перед перезагрузкой. Если за 300 с подтверждения нет — `esp_ota_mark_app_invalid_rollback_and_reboot()`. Падение или WDT до подтверждения → откат загрузчиком. Старая прошивка после отката видит в NVS чужой слот и пишет об откате в Telegram.
- **Проверка образа до стирания слота**: magic 0xE9, chip_id, `esp_app_desc_t` magic и совпадение `project_name`. `OTA_WITH_SEQUENTIAL_WRITES` стирает слот по мере записи.
- **Веб**: `POST /ota`, тело — сырой .bin (XHR из JS, без multipart), Basic-авторизация как у остальных страниц.
- **Telegram**: принимается document `*.bin` от разрешённого чата. В группе — только reply на сообщение этого бота или с @username в подписи (чтобы бот второго дома не прошился). `getFile` → скачивание `https://api.telegram.org/file/bot<token>/<path>` прямо в слот.
- **Важно**: перед перезагрузкой подтверждаем offset (`getUpdates?offset=…&timeout=0`), иначе после рестарта тот же файл придёт снова и прошивка пойдёт по кругу.
- Версия (`PROJECT_VER` в корневом CMakeLists.txt) видна в `/settings`, в сообщении о запуске и на веб-странице.
- После смены `sdkconfig.defaults` надо удалить `sdkconfig`, иначе старые значения остаются.

## Диагностика связи с BMS на веб-странице, версия 1.2.0

Нужно, чтобы по странице было понятно, правильно ли спаян UART.

- `jk_bms.c` считает итог каждого опроса (`jk_bms_get_diag()`): OK / нет ни байта / мусор без заголовка `4E 57` / битый или оборванный кадр / эхо собственного запроса (TX и RX замкнуты). Хранит первые 32 байта последнего ответа.
- `GET /bms` отдаёт JSON (с Basic-авторизацией): диагностика + напряжение, ток, SOC, температуры, ячейки.
- На главной странице блок «Связь с BMS» обновляется раз в 2 с: статус с подсказкой, что проверять, счётчики, сырые байты, сетка ячеек (макс. — красным, мин. — синим).
- **Тест реле** (`POST /relay`, `s=10/300/0`, максимум 600 с): блок «Реле зарядки (проверка)» с кнопками «Вкл на 10 с», «Вкл на 5 мин», «Выключить». Пин реле = тест ИЛИ решение логики (`st.relay_pin`), логика заряда при этом не трогается. Тест намеренно обходит failsafe «нет BMS», чтобы реле можно было проверить до подключения BMS, но не включается и прерывается, если сеть пропала (`GRID_OFF`) или напряжение ≥ порога «выключить». Уведомлений в Telegram нет, только лог.

- **`/charge_on` без BMS не включал реле, но бот отвечал «Заряд включён».** Это failsafe (нет BMS / сеть не GRID_ON → OFF), его оставили. Добавлен `control_block_reason()`: `/charge_on` и `/status` теперь пишут, почему реле не включается (нет BMS, сеть определяется, сети нет, заряжена).

## Цикл перезагрузок каждые 6.5 с и диагностика без USB, версия 1.3.0

**Симптом.** Бот не отвечал, плата перезагружалась каждые ~6.5 с (видно по счётчику опросов на /bms и по пингу). BMS, питание, веб-запросы и «ядовитая» команда Telegram были проверены и исключены по очереди.

**Причина (по логу с USB).** `task_wdt: ... - tg_send` на 6.49 с. В `sdkconfig.defaults` стояло `CONFIG_ESP_TASK_WDT_TIMEOUT_S=90`, но в ESP-IDF 5.5 допустимо 1…60: Kconfig молча отбросил значение и оставил 5 с. Задача `tg_send` ждёт очередь по 10 с между сбросами WDT → срабатывание через 5 с после её старта.

**Исправление.** Таймаут 60 с (`sdkconfig` и `sdkconfig.defaults`), в `telegram.c` `_Static_assert(CONFIG_ESP_TASK_WDT_TIMEOUT_S >= TG_POLL_TIMEOUT_S + 20)` — с коротким WDT прошивка не соберётся.

**Диагностика без USB (`diag.c`).**
- Кольцевой буфер 4 КБ в RTC-памяти (`RTC_NOINIT_ATTR`), переживает перезагрузку. Обычный лог — через `esp_log_set_vprintf()`, дамп паники — линкерным `--wrap=uart_hal_write_txfifo` (обработчик паники пишет в UART0 только через эту функцию; проверено по ELF).
- `GET /log`: причина перезагрузки, время работы, память, лог прошлого запуска с дампом и текущий лог. На главной — время работы и причина прошлой перезагрузки.
- После аварийной перезагрузки бот присылает причину и строку `Backtrace` (расшифровать: `xtensa-esp32s3-elf-addr2line -pfiaC -e build/JkongTelegramm.elf <адреса>`).
- Команда Telegram, во время обработки которой плата упала, после перезагрузки пропускается (update_id в RTC), бот сообщает какая.
- Буфер `sendf()` в web.c увеличен до 1024: длинные блоки с кириллицей обрезались.

## Команды, пришедшие с опозданием

При отключении света роутер перезагружается ~2 мин. Уведомления платы при этом не теряются: очередь отправки в RAM (32 места), повторы каждые 5 с, мёртвое keep-alive соединение пересоздаётся. А вот команды, отправленные боту во время отключения, раньше **молча** пропускались, если пришли позже 120 с.

Теперь (`telegram.c`, `TG_LATE_S` / `TG_MAX_AGE_S`):
- до 2 мин — как обычно;
- 2–30 мин — выполняется, ответ начинается с «⏱ Команда пришла с опозданием N мин»;
- старше 30 мин — не выполняется, но бот отвечает «⏭ … не выполнена: слишком старая, отправьте снова». Так же для файла прошивки.
- Ответ только на команды, адресованные этому боту (`/cmd@другой_бот` в группе по-прежнему игнорируется).

Не проверено на железе: выключить роутер на 3 мин, отправить `/status`, включить.

### Версия 1.3.1: время Telegram и время события
- **Часы сервера Telegram.** Из заголовка `Date` каждого ответа Bot API (`HTTP_EVENT_ON_HEADER`) берётся время сервера и смещение к `esp_timer`. По этим же часам Telegram ставит `date` в сообщениях, поэтому возраст команды верен сразу после перезагрузки, ещё до NTP (раньше в этом окне старая `/charge_on` выполнилась бы). Если системное время ещё не установлено — ставится по Telegram (`settimeofday`), NTP потом поправит. Разбор даты свой (`days_from_civil`), на железе расхождение с NTP 0 с.
- **Время события в задержанных уведомлениях.** У сообщения в очереди запоминается `esp_timer` постановки. Если при отправке оно пролежало > 60 с, в конец дописывается «🕒 Случилось в 14:32, доставлено с опозданием 3 ч 05 мин» (дата — если другой день). Задержка монотонная, поэтому верна, даже если время в момент события было неизвестно.
- Прошито по воздуху через веб-страницу, подтвердилось через 30 с.

### Версия 1.3.2: нехватка сокетов
В логе 1.3.0 было `esp-tls: Failed to create socket` → `sendMessage: ESP_ERR_HTTP_CONNECT`: Telegram не смог открыть соединение. Причина: `CONFIG_LWIP_MAX_SOCKETS=10` на всё устройство, а `HTTPD_DEFAULT_CONFIG()` разрешает веб-серверу 7 клиентских сокетов + 2 своих (слушающий и управляющий) = 9. Браузер держит к странице несколько keep-alive соединений (страница ещё и опрашивает `/bms` раз в 2 с), две-три вкладки или телефон + ПК — и веб-сервер забирает почти всё. Telegram нужно 2 сокета (приём и отправка; ещё один при скачивании прошивки), плюс DNS/SNTP. Сокеты, которые веб-сервер уже занял, при этом не освобождаются: `lru_purge` закрывает старое соединение только ради нового клиента веб-сервера.

Исправление: `CONFIG_LWIP_MAX_SOCKETS=16` (sdkconfig и sdkconfig.defaults), `cfg.max_open_sockets = 5` в web.c, `_Static_assert` на запас. Проверка на железе: 12 параллельных потоков к `/bms` 20 с — 235 ответов, 24 обрыва (LRU-вытеснение сверх 5), ошибок сокетов в логе нет, прошивка подтвердилась.

## Версия 1.3.3: 400 сообщений «перенапряжение при заряде» за ночь

При ночном заряде самая высокая ячейка доходит до порога BMS, BMS отсекает заряд, напряжение чуть проседает, тревога снимается — и так по кругу. Прошивка слала «🚨 Тревога BMS» на каждое появление бита → ~400 сообщений за ночь. Это штатная работа BMS (защиту по ячейке делает она, см. договорённости).

- `ALARM_SILENT_MASK` (config.h): бит 2 «перенапряжение при заряде» в Telegram не отправляется. В `/status` показывается как «ℹ️ BMS: … (BMS сама отсекает заряд по ячейке)».
- Остальные тревоги — с защитой от дребезга (`alarms_tick()` в control.c): одна и та же не чаще раза в час (`ALARM_REPEAT_S`), «✅ снята» — только если пропала на минуту (`ALARM_CLEAR_S`) и о её появлении сообщали. В лог пишутся только отправленные, чтобы мигание не вытесняло полезное из 4 КБ `/log`.
- Попутно: в `CMakeLists.txt` комментарий был испорчен двойной перекодировкой (PowerShell `Set-Content` при поднятии версии в 1.2.0) — восстановлен.

## Версия 1.4.0: «Реле всегда включено»

Пользователь попросил галочку рядом с «Реле зарядки», чтобы держать реле включённым постоянно. Управление **только с веб-страницы**, из Telegram не нужно.

Принятые решения:
- Пороги заряда, ночь, резерв и команды бота (`/charge_on`, `/charge_off`, `/auto`) в этом режиме не действуют. От перезаряда ячеек защищает BMS (по договорённости, защита по ячейке — её работа).
- **Failsafe сохраняется**: нет BMS или нет сети → реле OFF; когда вернутся — снова ON.
- Сохраняется в NVS отдельным ключом (`control/hold`), а не в `settings_t` — чтобы не менять формат блоба настроек. Переживает перезагрузку и OTA.
- Переключение галочкой — сразу, без паузы `RELAY_MIN_SWITCH_S`.
- Бот: в `/status` строка «📌 Реле включено постоянно», на команды заряда — предупреждение, что они не действуют. Уведомления о включении/выключении заряда работают как обычно (причина «включено постоянно (веб-страница)» / «снята галочка…»).
- Веб: `POST /relay` с `hold=1|0` (новый адрес не заводили: у веб-сервера 7 из 8 обработчиков), состояние в `/bms` → `rh`. При включении — подтверждение в браузере.

Проверено на железе: прошивка подтвердилась, галочка отображается, состояние читается. Само включение/выключение реле галочкой не проверялось (не хотелось слать уведомления о заряде), это первая проверка для пользователя.

## Проблемы, решённые по ходу

- **`idf.py` не находился.** `export.ps1` искал окружение `idf5.5_py3.14_env`, которого нет. Лечится так:
  ```powershell
  $env:IDF_PATH = "$env:USERPROFILE\esp\v5.5.1\esp-idf"
  $env:IDF_PYTHON_ENV_PATH = "$env:USERPROFILE\.espressif\python_env\idf5.5_py3.11_env"
  $env:PATH = "$env:IDF_PYTHON_ENV_PATH\Scripts;$env:PATH"
  . "$env:IDF_PATH\export.ps1"
  idf.py build
  ```
  На домашнем ПК пути могут быть другими.
- **Разовый segfault GCC** в `esp_lcd_panel_rgb.c`. Повторная сборка прошла.
- **Use-after-free в очереди Telegram** при «выбросить самое старое». Теперь при переполнении отбрасывается новое сообщение.
- **Гонки.** Сброс профиля идёт через задачу `control` (флаг), а переподключение STA вынесено в `net_task`.

Итог сборки: без предупреждений, приложение 0x107b00 байт, свободно 30 % раздела.
